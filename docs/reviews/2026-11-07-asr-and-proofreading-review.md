# 歌词识别与校对质量审查

## 结论和边界

目前**不能保证高识别率或时间轴精度**，也没有证据能够量化现版本对真实歌曲的平均提升。本文依据源码和现有测试审查；本轮没有运行真实 ASR 模型、人工核对歌曲或真实音频设备。合成数据上的回归测试只能证明指定边界行为，不能代表 CER、WER、漏行率或时间误差。

## 发现（按风险排序）

1. **P0：识别任务可能覆盖期间新增的人工歌词修改。** 修复前，`LocalProjectTranscriptionWorkflow.transcribeProject` 在耗时准备之后用旧 `project` 无条件写入识别状态；识别结束后获取 `latest`，却无条件把结果作为 `lyricDocument` 写回。开始前的歌词备份无法包含任务期间的新编辑。本轮以 revision 条件写保护启动及结果提交；冲突时拒绝覆盖并向调用方报告。结束清理只操作属于该任务的标记，且同样使用条件写。仍不能保证跨进程一致性、其他调用方的无条件写入安全或在所有存储故障后自动恢复状态。
2. **P1：缺少真实歌曲基准，无法证明识别率。** `docs/asr_quality_baseline.md` 和 `tool/asr_quality_report.dart` 已提供人工参考歌词与行召回、CER、重复率及时间误差评测；`tool/asr_transcript_eval.dart`、`tool/asr_preprocessing_ab_eval.dart`、`tool/forced_alignment_eval.dart` 覆盖不同侧面。当前工作区没有提供已人工核对的歌曲语料或真实基线；文档中的示例是合成测试，不能当成产品准确率。
3. **P1：校对中的空内容可能被标为双引擎一致。** `AsrConsensusAnalyzer` 使用 `LyricAlignmentService.lineSimilarity`；后者对两个归一化后为空的字符串返回 1。例如两条只含标点/音符的高分行可被判为 `agreement`，`AsrFirstPipeline` 进而给出绿色结果。识别融合层的 `AsrTextComparison` 已将空归一化文本视为不可比较，但这条校对路径尚未统一。本轮未修改该规则，建议下一阶段显式标为不可比较并保留人工复核。
4. **P2：时间相邻的次引擎行可能混入复核证据。** `AsrConsensusAnalyzer` 对每条主行收集所有落在前后 450 ms 补偿区间内的次行并拼接；相邻但实际不同的行可能被拼入，制造误报。该风险来自代码逻辑，不等于已测得真实歌曲误报率；需要用人工标注边界样本评估后再调整，以免漏掉跨行切分证据。
5. **P1：音轨和模型选择仍是识别质量瓶颈。** 转写输入优先人声轨、其次标准化轨、最后原曲；工程缺少可用人声时会回退原曲。当前产品没有自动人声分离能力，伴奏、和声和混响可能影响识别。双引擎结果会融合并可降级为单引擎，但两个模型的一致不等于正确；强制对齐只是时间证据，不验证歌词是否真实。

## 已有保护，不应误当成质量证明

- 普通时长音频默认整首处理，超长音频才分片；检查点包含配置指纹。
- 未评分不等于低置信；低置信或双引擎分歧进入复核，参考校对与强制对齐生成待审核证据而非保证歌词正确。
- 人工编辑与识别结果有备份、工程 revision 和部分条件写机制；本轮补上转写工作流的两处条件提交，不代表其他流程已经完成并发审计。

## 推荐后续阶段

1. 修复校对的不可比较文本误报；分别测试空白、标点、中文、韩文、英文和低置信输入，确保不会自动改动歌词。
2. 在本地私有 `corpus/` 准备至少 5–10 首获得使用授权的人工核对样本：中/英/日及可选韩文、快慢歌、重和声、长前奏/尾奏；记录来源、人工参考、音频哈希、模型/运行时版本、语言与参数，不把歌曲或隐私数据提交仓库。
3. 对相同音频、相同参数和参考分别跑 Whisper、Qwen、融合，报告每首的 CER/WER、行召回/精确率、重复率、边界误差及失败/降级情况；保留分语种与分难度结果和音频缺失情况，不能只看总体平均值。采用现有工具及其适用条件，WER 使用单独的文本评测工具。
4. 基于该基线逐项 A/B 测试输入轨、解码参数、语言配置、融合分段和时间对齐；只有回归测试和真实样本证据支持时才调整阈值或默认值。现阶段不声称自动分离、模型升级或任何参数调整一定提升质量。
