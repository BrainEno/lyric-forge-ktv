# [2026-11-01 20:39] Let highest quality degrade to Whisper instead of refusing the song

- Scope: Phase 1 item 1.5 of the recognition-quality roadmap. Highest quality used to be a prerequisite rather than a capability: the service refused to start unless both engines were configured, the runtime preflight required every component to be installed, and the queue paused on any missing piece. One driver update, one model file moved or one exhausted GPU therefore left the user unable to recognise a single song, even though Whisper was installed and working. The mode now means "use two engines when both are usable, otherwise produce a Whisper draft and say so", and the downgrade is recorded on the document and shown in the project panel. Verification lives in five new service tests, two runtime-status tests, two preflight tests, one queue-recovery test and an updated configuration test; the earlier configuration test had explicitly asserted that a Whisper-only highest-quality setup was unusable, so it had to be rewritten rather than deleted.

- Notes: Two deliberate exceptions keep the fallback honest. Input errors (missing or corrupt audio) do not degrade, because Whisper would fail identically and running it only collects the same complaint twice. Cancellation never degrades. When the degraded run itself fails, the thrown error carries both the degradation reason and Whisper's own error, so the message names the root cause rather than just "the fallback failed too". The degraded document keeps `qualityMode: highestQuality` (what was requested) and states the reality through `degraded` / `degradationReason` / `degradationDetail`; overwriting the mode would erase what the user asked for, which is the exact information the project panel exists to show. That is the formatter's output, not a rewrite. No real-song measurements are claimed; this is a routing and reporting change.
