# [2026-11-03 00:02] An undo stack for the lyric editor

- Scope: Phase 3 item 3.4 (plan table; the "保存并返回" half of the row was already finished in 3.1). The editor could only undo one thing: reference alignment, once, and only until the next edit. A mistyped line, a deleted row, an offset nudged the wrong way, or a proofreading proposal applied by mistake had no way back — the only escape was discarding the whole document by refusing to save. For a screen whose entire purpose is line-by-line correction, that is the most expensive kind of defect: five bad edits meant either starting over or hand-reverting each one.

- Notes: Three decisions worth keeping. First, the history stores *pre-edit* documents and is recorded at the moment of the edit, so the stack describes what the user did rather than what the code touched — including review marks, which are metadata edits the old snapshot ignored. Second, consecutive edits to the same line within two seconds collapse into one step; without that, retyping a line would consume the whole 50-step budget and the acceptance case would only survive three or four real mistakes. Third, loading a project clears the stack: undoing across a load would restore another song's lines, which is worse than not being able to undo. Not done on purpose: no "revert to last save" (it would overlap the unsaved-changes interceptor) and no persistence (undo must not walk back into a document that no longer matches disk). Testing note: the first shortcut harness had no focused node, so `CallbackShortcuts` never saw the events — key events bubble up from the focused node, and the widget under test only observes events raised inside its subtree; the harness now gives it an autofocused child, the way the editor's list does.
