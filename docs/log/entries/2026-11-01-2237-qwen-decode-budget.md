# [2026-11-01 22:37] Size the Qwen decode budget from the song, not from a constant

- Scope: Phase 1 item 1.6's cheaper half — review R9 (`max_new_tokens` was the literal `1024` for every request). Reading the upstream runtime to fix it turned up something that changes the severity: `max_new_tokens` is a **per-chunk** budget (`run_asr_on_chunks_batched` passes it to every chunk), and the chunk ceiling is `MAX_ASR_INPUT_SECONDS = 1200.0`, not the 180 seconds this repository's documents claimed. A four-minute song is therefore a *single* chunk, so those 1024 tokens had to cover the entire lyrics — about 700–900 tokens for dense Chinese, plus the prompt. The old value sat right at the edge of truncating the last verse, silently, with HTTP 200. The budget is now derived from the normalized audio length, and two measurements are recorded so a future quality report can reason about truncation without guessing.
- Files: `lib/features/transcription/domain/models/qwen_decode_budget.dart` (new: the chunk cap, the duration-from-bytes helper, the budget formula), `lib/features/transcription/data/services/qwen3_asr_native_transcription_service.dart` (measures the normalized WAV once, sends the derived budget, records it plus `transcriptCoverage`), `lib/features/transcription/data/services/asr_process_supervisor.dart` (timeout policy now reuses the shared duration helper instead of its own copy of the byte math), `test/features/transcription/qwen_decode_budget_test.dart` (new), `docs/high_quality_asr.md`, `docs/lyric_proofreading_v2_plan.md`, `docs/reviews/2026-10-31-recognition-quality-and-ux-deep-review.md` (R9 marked fixed; the incorrect 180 s chunk claim corrected in R1 and R9), `docs/log/entries/2026-11-01-2237-qwen-decode-budget.md`, `docs/handoff.md`, `docs/work_log.md`, `docs/work_log_archive.md`.

- Notes: The formula is `max(1024, 256 + min(audio_seconds, 1200) × 8)`, not the `max(512, seconds × 6)` the review suggested: eight tokens per second covers roughly five CJK characters per second and leaves headroom for punctuation, and the 1024 floor keeps every request at least as generous as the constant it replaced, whereas a 512 floor would have made short clips tighter than the status quo. Two measurements now travel with every draft: `maxNewTokens` (what was actually sent) and `transcriptCoverage` (how far the recognised lyrics reach into the audio). Coverage is recorded deliberately without a threshold — songs routinely end with an instrumental outro, and turning that into a warning would repeat the R8 mistake of presenting a number as a verdict. What is still *not* claimed: the `/v1/transcribe` response carries no `finish_reason` and no token count (only the OpenAI-compatible endpoints do), so "the model really did hit the cap" remains unknowable from the current contract. Documentation corrected alongside: three places asserted the runtime chunks at 180 s; the current upstream source contains no such constant, and the repository documents now say 1200 s with the symbol name, so the next reader can check it.
