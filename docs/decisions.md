## D-001 导出的 LRC 使用烘焙后的有效播放时间

- 日期：2026-10-09
- 背景：不同播放器对 LRC `[offset:<ms>]` 正负方向解释不一致，导出的时间轴会在别的播放器上整体错位。
- 决定：导出时把工程 `globalOffset` 直接烘焙进每行时间戳，导出文件不再单独写 `[offset]`；工程 manifest 仍保留独立 offset 供编辑。
- 影响：跨播放器对齐一致；代价是重新导入后 offset 分解被压平，负的最终时间戳钳制到 `00:00.000`。
- 状态：生效
- 来源：[2026-10-09 12:03 条目](log/entries/2026-10-09-1203-lrc-effective-playback-timestamps.md)

## D-002 KTV 麦克风链路采用 record + flutter_soloud

- 日期：2026-10-09
- 背景：早期评估的 `audio_io >=0.3` 与现有 `mobile_scanner 7.4.x` 在 `web` 依赖上不可共存。
- 决定：改用 `record 6.2.1` 采集麦克风 PCM16、`flutter_soloud 5.1.2` 做低延迟输出，不降级扫码功能。

- 状态：生效
- 后续修订（2026-10-31）：实际锁定为 `flutter_soloud 4.1.7`（见 `pubspec.yaml` 中带原因的 pin 注释）：5.x 引入的 `native_toolchain_c` 的 `meta` 约束曾与当时的 Flutter 版本冲突，4.1.7 已覆盖 KTV 监听所需的 buffer-stream API。是否升级 5.x 由 issue #228 跟踪；`record 6.2.1` 部分不变。
- 来源：[2026-10-09 12:36 条目](log/entries/2026-10-09-1236-low-latency-ktv-microphone-monitoring.md)

## D-005 歌词可用性以解析结果为准，队列标记只是缓存

- 日期：2026-10-19
- 背景：播放条目上的 `hasLyrics` 在入队时写入，歌词工程被删除或稍后生成时都不会自动更新，播放器底栏、快速播放与 Now Playing 会给出互相矛盾的"打开歌词 / 导入歌词"判断。
- 决定：`resolvePlaybackLyrics` 返回结构化的 `PlaybackLyricsResolution`（工程 id、是否真的带歌词、是否修复或清除死链），由 `resolveAndSyncPlaybackLyrics` 把权威结果经 `PlaybackSessionService.updateItem` 回写队列；应用壳层挂载 `PlaybackLyricsAvailabilitySync` 监听当前条目变化，各播放面继续同步读取回写后的标记，不各自重跑解析。远程流的标记由远端目录维护，不参与回写。
- 影响：死链清理与"入队后才生成歌词"两种情况都会收敛到同一判断；代价是每次切歌多一次内存内的解析（媒体元数据与工程列表均已缓存）。工程仓库读取异常仍被当作"没有工程"，属于既有硬化缺口。
- 状态：生效
- 来源：[2026-10-19 22:28 条目](log/entries/2026-10-19-2228-unify-playback-lyrics-availability.md)

## D-006 参考歌词纠正默认逐行确认，手动编辑需显式解锁

- 日期：2026-10-20
- 背景：C2 的 80% 阈值批量应用无法让用户在处理低置信行前看到字符级差异；直接覆盖本次手动改过的行也违反"不静默覆盖"。
- 决定：参考歌词纠正以逐行 diff 卡为默认入口；默认勾选相似度 ≥80% 且未手动编辑的行，低置信行需手动勾选；本次手动编辑过的行默认锁定，必须二次确认才能替换；时间轴是独立整体开关（参考与草稿 1:1、全部带时间戳、本次无手动编辑时开放）；漏行只列入待处理清单，不自动插入（该漏行规则由 D-008 取代）。
- 影响：C2 的摘要对话框被 C3 逐行确认取代；应用仍走显式保存，备份与溯源 metadata 保留；阈值自动采纳与显式选择在 `ReferenceAlignmentApplier` 中共存。
- 状态：部分已取代（仅漏行规则由 D-008 取代，其余生效）
- 来源：[2026-10-20 11:53 条目](log/entries/2026-10-20-1153-reference-alignment-per-line-review.md)

## D-007 对齐备份是单槽快照，恢复需二次确认且不自动保存

- 日期：2026-10-20
- 背景：`metadata['referenceAlignmentBackup']` 是参考对齐应用前写入的唯一兜底快照，此前没有恢复入口；恢复属于破坏性操作，会覆盖用户当前编辑中的歌词。
- 决定：恢复入口仅在备份存在且可解析时显示；确认对话框必须展示备份时间/来源/格式/行数并明确覆盖警告，破坏性按钮文案为"恢复并覆盖"；恢复成功后消耗备份键（单槽，不允许重复恢复旧快照），写入 `referenceAlignmentRestore` 溯源并保留备份自带的旧 `referenceAlignment`；恢复只替换编辑器内存文档并标记未保存，由用户显式保存落盘；恢复后清空会话级手动编辑行索引，避免旧索引错位。
- 影响：取消或解析失败不修改任何状态；恢复后 `_hasChanges = true`，未保存前再次对齐会覆盖该快照；"手动编辑保护是会话级"的既有语义不变。
- 状态：部分已取代（会话级手动编辑保护与恢复清空索引由 D-009 取代）
- 来源：[2026-10-20 12:28 条目](log/entries/2026-10-20-1228-reference-alignment-backup-restore.md)

## D-008 纯文本参考可补全漏行，时间由相邻锚点推断

- 日期：2026-10-20
- 背景：用户常能从网络拿到完整但无时间轴的歌词；C1–C3 只纠正已有行，漏行仍需暂停后手工插入，无法满足"粘贴整段歌词后自动补全并建立时间轴"。
- 决定：复用纯文本参考对齐，对 `missing` 参考行生成插入计划；漏行插到后一个已匹配 ASR 行之前（无后锚点则追加末尾），连续漏行保持参考顺序；纯文本漏行在前一匹配行结束与后一匹配行开始之间平均分配时间（至少 10ms），末尾漏行每行默认 5 秒；带时间戳参考漏行优先用参考时间；锚点之间夹着未匹配 ASR 行或空隙不足时标记 `requiresConfirmation`，逐行确认中默认不勾选；非歧义漏行默认勾选。
- 影响：C3 的"漏行不自动插入"由本决定取代；应用仍走显式保存，单槽备份与 `referenceAlignment` 溯源保留，并新增 `insertedReferenceCount`/`insertions`；不做跨行重组，断句/合并差异需用户确认；插入不删除、不重排原有行，也不裁剪相邻行已有结束时间。
- 状态：生效
- 来源：本条目对应的任务条目（C4 纯文本参考补全漏行）

## D-009 手动编辑保护按稳定行标识持久化，对齐溯源显式标注索引基准

- 日期：2026-10-21
- 背景：手动编辑保护此前是 `Set<int>` 行索引，插入/删除/补行后容易错位，且只活在单次编辑器会话里；重开工程后保护丢失，再次运行参考对齐会静默覆盖用户改过的歌词。`referenceAlignment` 里的行号也没有说明是应用前还是应用后，补行后无法回溯到具体行。
- 决定：`LyricLine` 增加可选稳定标识 `id`；编辑器用 `Set<String>` 记录手工编辑行，加载时补齐缺失标识，保存时把 `manuallyEditedLineIds` 写入文档 metadata，重开时恢复；受保护索引由标识在现有行序中派生，不再手工平移。对齐结果额外暴露 `appliedIndexByOriginalIndex` 与插入行 `appliedLineIndex`；`metadata['referenceAlignment']` 由纯构建器生成，固定 `indexBase: 'pre-application'`，纠正/补入/跳过的保护行都附带 `lineId`。
- 影响：插入、删除、参考补行、备份恢复后保护仍跟随同一行；旧工程没有标识时重开会补新标识，旧标记自然失配（与旧的"会话级"行为一致，不会误保护）；`insertions[].asrLineIndex` 字段在 metadata 中改名为语义明确的 `appliedLineIndex`（无读取方依赖旧键）；编辑器的索引平移函数 `_shiftEditedIndices` 删除。
- 状态：生效
- 来源：[2026-10-21 11:45 条目](log/entries/2026-10-21-1145-e4-marker-persistence.md)

## D-010 参考对齐按"正确性优先"批量应用，并记录时间来源

- 日期：2026-10-21
- 背景：仅按相似度阈值批量采纳会把歧义行、结构差异行和弱匹配行一起覆盖；纯文本时间插值无法区分参考时间戳、ASR 映射与推断时间；一次性应用后也只能依赖保存前的备份恢复。
- 决定：配对分数为 `similarity - 0.7`，相似度 ≤0.7 的弱匹配让位给 gap；歧义由前向/后向 DP 的全局证据判定；一对多/多对一仅标记结构差异，不隐式合并/拆分。安全批量只含高置信、无歧义、无结构差异、非手动编辑的 `replace` 行，其余进入需确认组。时间来源按稳定 `lineId` 写入 `metadata['timingProvenance']`（`reference` / `mappedAsr` / `interpolated` / `estimatedTail` / `manual`），文字置信度独立；已有 `manual` 不覆盖。应用前比较时间轴，严重的新冲突需用户明确保留或撤销。应用后提供仅内存的撤销快照（文档、`globalOffset`、行标识、手动编辑集合、选中行、未保存状态），后续编辑/保存/恢复备份使快照失效，落盘仍只由显式保存触发。
- 影响：低置信与歧义行不再随"全选高置信"被批量替换；弱匹配从 `lowConfidence` 改为漏行/多余行；导入 LRC 冲突与偏移修复警告原样进入审核界面，不静默处理。
- 状态：生效
- 来源：[2026-10-21 14:03 条目](log/entries/2026-10-21-1403-reference-alignment-safe-batch-and-undo.md)

## D-011 对齐引入的时间轴冲突先做保守自动修复，修复行记录 `autoRepaired`

- 日期：2026-10-21
- 背景：E5 的冲突门只问"保留或撤销"，不会先尝试任何可靠可推断的修复；逐行对比在应用后立即关闭，用户难以复核本次改动。
- 决定：应用参考对齐后、弹出冲突对话框前，先跑纯 Dart 的保守修复：只收紧"明确重叠"行的结束时间到下一行开始时间、按已知音频总时长裁剪受影响行、并在固定锚点之间用文字长度权重重新分配来源为 `interpolated`/`estimatedTail` 的插入行；绝不移动参考/ASR/手动起始时间，不隐式重排歌词，估算行放不进间隙时保持原样并继续报校验冲突。被修复行的时间来源记为 `autoRepaired`；修复数量计入应用摘要。应用后 undo 快照有效期内提供"查看逐行对比"，按稳定 `lineId` 展示字符与时间差异并可试听。
- 影响：新引入的重复/倒退起始时间等不可推断冲突仍走明确的保留/撤销门；`metadata['timingProvenance']` 新增 `autoRepaired` 值；对比面板依赖应用前快照，快照失效后入口随之禁用。
- 状态：生效
- 来源：[2026-10-21 15:47 条目](log/entries/2026-10-21-1547-post-apply-diff-and-timeline-auto-repair.md)

## D-012 状态管理必须服从既有服务事实源并限制在局部子树

- 日期：2026-11-03
- 背景：编辑器文档状态由屏幕手动协调，而播放/session 状态已由 app-scoped services 通过 streams 发布；全局复制播放状态会制造第二事实源。
- 决定：编辑器文档 controller 使用 `ChangeNotifier`，仅在成功状态变化后通知，并由局部 `Provider/Selector` 订阅所需快照；加载必须在监听子树构建前完成。播放/session 服务仍是唯一事实源：播放条继续消费现有 streams，桌面条把同一 session 快照传给队列/模式控件以避免重复订阅；短生命周期控件状态继续留在 widget。
- 影响：Provider 不成为全局 service locator，不创建第二个播放器/队列，也不要求把全部编辑器 UI 状态搬进 store。识别与歌词编辑语义保持由现有 controller/service 测试保护。
- 状态：生效
- 来源：[Phase 4.4 最终交付记录](log/entries/2026-11-03-2113-phase44-state-management-final.md)

## D-013 状态管理选型及依赖装配边界

- 日期：2026-11-07
- 背景：局部 widget 状态、异步服务状态与编辑器文档状态生命周期不同；误把 Provider 当全局容器或复制播放状态会造成双重事实源。D-012 已约束编辑器与播放状态，本决定补充新功能的选择依据。
- 决定：短生命周期、只影响当前 widget 且不跨导航保留的交互状态使用 `setState`，在 dispose 后不得继续更新。播放、队列和长任务等已有领域服务保持为事实源，通过服务契约与 Stream 发布异步状态；订阅者负责释放订阅并处理错误、完成与取消。需要在同一子树共享可变 UI 文档且有明确所有者时，可使用 ChangeNotifier + Provider；只读取必要字段时使用 Selector，controller 在创建子树前初始化，由创建者负责释放。一次性不可变配置通过构造参数传递，不为了方便而新增全局 store。
- 影响：先复用现有服务/状态，不为同一实体再创建平行事实源；选择其他方案需说明生命周期、所有权、错误与取消行为并补相应测试。依赖在 `lib/app/` 组合根创建并注入 screen/use case；feature 不反向引用 app shell 或 service locator。跨 feature 通过稳定 domain 契约协作，现存依赖环和跨 feature presentation 引用需逐步收敛，不能因为存在基线而继续扩大。assembly、分层与依赖图契约是静态保护，不替代实际行为测试。
- 状态：生效
- 来源：[Phase 4.4 状态管理](log/entries/2026-11-03-2113-phase44-state-management-final.md)；issue #235。

## D-014 Whisper 只接收工程元数据提示；仅副引擎行只作为待复核候选

- 日期：2026-11-14
- 背景：#448 之前 Whisper 拿不到任何歌曲上下文，只有 Qwen 用到了 `request.context`。双引擎融合会把 Whisper 的不同断句当成新行插入，也可能让只有 Whisper 识别到的真歌词在界面上不可见。另一方面，给模型喂参考歌词、编造置信度，或者自动合并不确定的行，都会污染第二引擎的证据。
- 决定：
  - 新增纯 Dart 的 `WhisperDecodingPolicy`。只有运行时 `-h` 实际列出的参数才会使用，目前是 `--prompt` 和 `--suppress-nst`。提示词只来自 `RecognitionHints`（歌名、歌手、专辑、用户专有名词）；这个类型没有歌词字段。提示词按语言生成、清洗，并限制在 200 UTF-8 字节以内。运行时不支持时回退到标准参数，并记录回退原因。
  - 解码 profile、提示和能力签名都进入 chunk 断点指纹。
  - 融合时，只有满足以下全部条件的副引擎行才算断句差异，计数但不插入：时间重叠、相邻主引擎行连续、文字被这些主行拼接后的文本包含。
  - 其余仅副引擎行作为「建议补入」插入，并在 `secondaryOnlySuggestions` 中精确记录；不丢弃，也不合并进主引擎行。
  - 编辑器里，「保留」只写复核决定，「拒绝」是可撤销的删行。两者都只改未保存的文档，不自动保存。
  - 识别摘要卡只显示计数；缺数据时显示「不可用 / 未采集」，不显示百分比。
- 影响：
  - 旧的 whisper.cpp 运行时照常工作（使用标准参数）。
  - 切换 profile 会让旧的 chunk 断点失效。
  - 质量工具新增 WER、`secondaryOnlyPrecision` 和 `secondaryRetention`；retention 低于 1.0 视为融合退化。
  - 真实模型上的收益尚未验证，需要按 Windows 手工步骤采集。
- 状态：生效
- 来源：issue #448；[2026-11-15 10:45 条目](log/entries/2026-11-15-1045-improve-lyric-asr-recall-and-review.md)

## D-015 简繁字形：比较一律折叠，写回只在识别落盘与用户确认时发生

- 日期：2026-11-15
- 背景：Qwen 与 Whisper 输出的简繁字形不稳定，同一首歌常出现「我爱你 / 頭髮飄在風裡」混排。比较路径把「愛」和「爱」当成不同字，会制造假分歧，污染融合、参考对齐、V2 证据与复核排序；直接改写用户歌词又可能误伤日文汉字、手工修改和一简对多繁（发/發/髮）的字。
- 决定：

  - 设置「中文字形」：自动（统一少数派行，默认）/ 保持原样 / 简体 / 繁體（台灣）/ 繁體（香港）。新识别草稿在工作流落盘前按设置统一一次，并把结果写入 `transcription.chineseScript` 与文档 metadata `chineseScriptUnification`（目标、字表 revision、转换行 id）。含假名或谚文的行、主要是日文/韩文的文档不转换；自动模式只改少数派行与混用行，通用字行不动；票数相同且语言标签无倾向时不改。
  - 繁体目标让 Whisper 的提示模板也使用繁体词（專輯）；用户填写的歌名、人名保持原样。模板字形进入断点指纹。

  - V2 证据：草稿与主引擎原文逐行比较时，只有用同一 revision 的字表重放记录的转换能得到当前文本，才视为同一份转录；其他差异仍是人工修改。

  - 字表更新必须同时改 revision；旧 revision 的记录不能再证明文本未被手改，相关证据降为只读审计。
  - 质量报告新增 `writtenCharacterErrorRate`、`scriptOnlyCharacterEditCount`、`scriptInconsistentLineCount` 与字形统计；原有 CER 变为字形折叠后的值。

## D-017 批量文字工具：只改文字，先预览，用户选定的写法视为手动编辑

- 日期：2026-11-16
- 背景：没有参考歌词时，校对最费时的是三类重复劳动：同一个词每次都识别错，要逐行改；副歌重复四遍，其中一两遍被识别成别的字；识别结果带着句末标点、全角字母、[音乐] 标记，以及识别器在静音处编造的字幕水印（谢谢观看、字幕由 Amara.org 社区提供）。编辑器此前只能一行一行处理。
- 决定：
  - 「校对」菜单新增三个工具：批量查找替换（Ctrl+H，macOS 为 Cmd+Shift+H）、重复段落一致性检查、清理识别文本。三者都是纯领域服务（`lyric_find_replace_service.dart`、`lyric_repetition_consistency_service.dart`、`lyric_text_cleanup_service.dart`）加一个预览对话框，结果作为一次可撤销的批量修改写入编辑中的文档，不自动保存。对话框打开期间文档若有变化，结果不应用。
  - 只改文字，不改时间、行 id、置信度。清理工具删除整行时，行索引类复核证据按 `LyricIndexedReviewMetadata.afterRowRemoved` 平移。
  - 默认跳过手动编辑过的行，需要用户勾选才处理。查找替换和重复行统一写入的是用户明确选定的文字，这些行随后加入手动编辑标记，之后的智能校对不会再覆盖。清理工具是机械规则，不加标记。
  - 查找替换默认忽略简繁差异和英文大小写，可选英文全词匹配；替换文字按用户输入原样写入。
  - 重复行分组的比较键是：字形折叠，转小写，去掉空白和标点；至少 4 个字符才参与比较。编辑距离不超过较长一方的 25%（最少 1）才算近似。分组以出现次数最多的写法为种子，不做链式合并。推荐顺序：唯一一种含手动编辑行的写法 → 严格多数 → 次数相同时置信度差至少 10 分（只推荐，不预选）→ 不推荐。只有明确的情况才预选：手动确认，或多数写法至少出现 2 次、且是其他每种写法次数的 2 倍以上。两种写法都反复出现时，更可能是有意的歌词变化，交给用户决定。
  - 清理规则逐条可关。默认开启：空白整理、全角 ASCII 转半角、去标注、句中标点改空格、去句末标点（保留 ？！）、删除字幕水印行、删除纯标注行。默认关闭：去掉汉字间空格（很多歌词用空格分乐句）、删除空行（可能是刻意留的间隔）。ASCII 逗号只在紧邻 CJK 文字时替换，小数点不动，谚文之间的空格永远不删。字幕水印要占整行至少 60% 才删除。
  - 质量报告新增 `asrBoilerplateLineCount` 与 `repetitionInconsistentLineCount`，使用同一套规则，便于衡量识别管线在这两类问题上的改进。
- 影响：
  - 字幕水印和标注词表是经验列表，新的识别器幻觉需要补充到 `LyricTextCleanupService.asrBoilerplateFragments` / `annotationWords`。
  - 重复行检查只依据歌词自身，不读音频；推荐写法可能错，对话框提供逐组试听与改选。
- 状态：生效
- 来源：自选任务（无参考歌词时的校对效率）；[工作日志](log/entries/2026-11-16-0900-add-batch-proofreading-tools.md)

## D-018 断行整理：拆分与合并只改结构，分界时间来自暂停位置或字数比例

- 日期：2026-11-16
- 背景：识别器按停顿切分，不按歌词行切分。识别稿常见两种结构问题：一行装了两句歌词；一句被切出一个一两个字的碎片。编辑器此前没有拆分或合并操作，只能删掉一行、再插入一行并手填时间。识别摘要也只报告引擎分歧和待复核数量，不提示可以批量处理的机械问题。
- 决定：
  - 纯领域服务 `LyricLineStructureService` 负责拆分与合并。
    - 拆分不改写文字：两半就是断点两侧的原文，只去掉断点处的空白和软标点（，、；：/|）。
    - 分界时间优先取暂停中的播放头（必须落在本行内，且两半各留至少 0.2 秒）；否则按“演唱权重”比例分配：汉字、假名、谚文各计 1，拉丁字母和数字计 0.5，标点和空白计 0；结果按 10 ms 取整，并限制在原时间段内。
    - 自然断点是空白和句读标点，取最接近演唱中点的一处，标点在接近时优先。没有断点时只允许在两个汉字或假名之间断开，不会拆开拉丁单词或谚文单词。
    - 合并：汉字、假名、CJK 标点之间直接相连，其余情况加一个空格；起止取两行的并集；置信度取较弱的真实分数，占位分数不会盖过真实分数，启发式分数保留启发式来源；保留第一行的 id。
  - 编辑器操作：检查器新增“拆分此行”（Ctrl+Enter，macOS 为 Cmd+Enter，光标在文字中间时从光标处断开）和“与下一行合并”，列表右键菜单新增同样两项。两者都是一次可撤销的编辑。被拆分或合并的行视为手动编辑（与改文字一致），之后的对齐和智能校对不会覆盖。该行的行索引类复核证据丢弃（它描述的已不是现在的文字），后面的行按 `LyricIndexedReviewMetadata.afterRowSplit/afterRowsMerged` 平移。
  - 「校对」菜单新增批量工具“整理断行”（`LyricStructureAdvisor` + 预览对话框）：
    - 演唱权重超过 20 的行建议拆分。
    - 权重不超过 2 或时长不足 0.7 秒的碎片行，若与相邻行间隔不超过 0.35 秒、且合并后不超过 20，则建议并入间隔更短的一侧。
    - 每行最多出现在一条建议里。手动编辑过的行、空行、“建议补入”行、字幕水印行和纯标注行一律不动；后两类交给清理工具删除，不能并进歌词。
    - 没有自然断点、只能从中间断开的拆分只列出，不预选。批量工具是机械规则，与清理工具一样不加手动编辑标记。
  - 识别摘要卡新增“可批量整理”提示，每个提示直接打开对应工具：字幕水印/标注行（清理识别文本）、过长行与碎片行（整理断行）、重复句写法不一（重复段落一致性检查）。计数与工具打开后实际提供的内容使用同一套规则。结果按文档实例缓存，因为编辑器会随播放进度频繁重建。
  - 质量报告新增 `overlongLineCount` 与 `fragmentLineCount`。没有时间戳的行不计入碎片。
- 影响：
  - 阈值（20、2、0.7 秒、0.35 秒）是经验值，需要用 #413 的真实歌曲基线校准。
  - 按字数比例估算的分界时间只是起点；提示文案和预览都要求试听后再微调。
  - 编辑器屏幕仍在 1200 行预算内：行编辑的收尾逻辑合并为 `_applyRowEdit`；播放头是否可用由 `LyricEditorContent` 判断。
- 状态：生效
- 来源：自选任务（识别稿的断行问题）；[工作日志](log/entries/2026-11-16-1230-add-line-structure-editing.md)

## D-019 时间轴工具与多格式导出：只按规则修复，推测性修改默认不勾选

- 日期：2026-11-16
- 背景：
  - 时间轴校验器早已能逐行指出问题：重叠、结束不晚于开始、顺序颠倒、超出音频。但自动修复只在参考歌词对齐流程内部使用，用户手里的识别稿或手工打轴稿没有入口。
  - 全局偏移只能整首平移。识别稿后半段越来越偏，或换了速度不同的音频版本时，只能逐行改时间。
  - 导出只有 LRC，并且只写开始时间，播放器在间奏时会一直停留在上一句。导入早已支持 SRT/WebVTT/TXT，导出却不支持。
- 决定：
  - **检查时间轴**（`LyricTimelineRepairPlanner` + 预览对话框，「校对」菜单和识别摘要的“时间轴问题 N 行”提示）：
    - 规则修复：负开始时间移到 0:00；结束不晚于开始时按演唱权重估算结束时间（每单位 0.35 秒，限制在 1–6 秒，不越过下一行开始）；与下一行重叠时收尾到下一行开始；不足 100 ms 的空隙闭合；超出音频的结尾收到音频末尾。这些修复默认勾选。
    - 顺序颠倒：只有当去掉某一行能恢复相邻行顺序、而去掉另一行不能时，才判定它是错位行，并把它挪到上一行之后、下一行之前。这是推测，默认不勾选，提供试听。无法判定时列入“需要人工定点”。
    - 任何修复都不会产生短于 0.2 秒的行，不改文字和行序，不动手动编辑过的行（列为已跳过）。修复后的行在 `timingProvenance` 中记为 `autoRepaired`。对话框按当前勾选实时显示“应用后仍有 N 行冲突”。
  - **平移 / 伸缩时间轴**（`LyricTimingShiftService` + 对话框）：
    - 范围可以是全部、从选中行到末尾、或任意起止行。
    - 平移：范围内所有起止时间加同一个偏移。两点校准：把两行钉到新的开始时间，其余时间按线性比例映射。比例超过 2 倍、小于 1/2 或顺序颠倒时拒绝，视为输入错误。
    - 开始时间小于 0 的行夹到 0:00 并保持时长；超出音频的结尾夹到音频末尾。结果列出新引入和顺带消除的时间冲突。暂停中的播放头可以作为目标时间。
    - 时间输入接受 `1:23.45`、`83.45`、`-0.5`、全角冒号等写法。
  - **多格式导出**（`LyricExportEncoder`，纯领域代码）：
    - 支持 LRC、SRT、WebVTT、纯文本，导出前有格式选择和文件预览。
    - 所有格式统一：应用全局偏移、负时间夹到 0、跳过空行、按开始时间稳定排序。
    - 字幕格式中，没有有效结束时间的行给 3 秒，与下一条重叠时截到下一条开始，以免两句同时显示。
    - LRC 可选“间奏处清屏”（导出对话框默认开启）：停顿不少于 1.5 秒处和最后一行后写一个空时间标签。导入时把空时间标签当作上一行的结束时间，因此往返不丢失结束时间。WebVTT 会转义 `& < >`，导入时还原。
    - 定时格式导出前提示时间轴问题行数。`exportLrc`/`encodeLrc` 保持原有输出不变。
  - 导出流程从编辑器屏幕移到 `LyricExportCoordinator`，并记住本次会话最后一次选择的格式和选项。
- 影响：
  - 估算参数（每单位 0.35 秒、1–6 秒、0.2 秒下限、1.5 秒清屏、4 秒分段）是经验值。
  - 健康提示的时间轴计数不含“超出音频”这一项，因为摘要卡拿不到音频时长；打开工具时会结合音频时长完整检查。
- 状态：生效
- 来源：自选任务（时间轴校对与交付格式）；[工作日志](log/entries/2026-11-16-1800-add-timing-tools-and-export-formats.md)

## D-020 打轴、语速异常检查与卡拉 OK 导出：时间来自人或按全曲语速推断，逐字时间明确标为估算

- 日期：2026-11-17
- 背景：
  - 识别稿的时间整体偏移或逐行错乱时，现有手段只有逐行“标记人声起点 / 终点”或两点校准，重打一整段很慢。KTV 制作里最常用的“打轴”（边听边按键）没有入口。
  - 识别稿的文字和时间常常一起出错：一行在一秒里“唱”十几个字，多半是结束被截在换气处或识别多出了字；四个字占九秒，多半是跨过了间奏或漏了一句。时间轴检查只看重叠和顺序，发现不了这类问题。
  - 导出只有逐行时间。卡拉 OK 视频和逐字高亮播放器需要每个字的时间（ASS `\k`、逐字 LRC）。
- 决定：
  - **打轴**（`LyricTapSyncSession` 纯状态 + `LyricTapSyncDialog`，「校对」菜单入口）：
    - 从选中行开始，每按一次空格（或按下大按钮）记录当前行的开始并换到下一行。暂停时第一次按键只开始播放，不打点。
    - “轻点”模式下，未单独结束的行收尾到下一行开始；与下一行相隔超过 8 秒视为间奏，改用原时长（不超过 8 秒）或按字数估算。“按住”模式按下开始、松开结束；任何模式下 Enter 都可以结束当前行。
    - 两次按键相隔不到 120 ms 视为按键抖动并忽略。按键时间早于上一行开始，视为用户已回退，自动丢弃该时刻之后的打点再重打。退格撤回（先撤结束，再撤开始，并回到该行前 2 秒）；← 后退 3 秒并撤掉之后的打点。
    - 按键时间 = 播放器最近一次上报的位置 + 上报后经过的时间 × 播放速度（最多外推 600 ms），因为播放器每秒只上报几次位置。可选反应补偿 0/80/150 ms（按播放速度折算），可以用 0.5×/0.75× 慢速打轴；关闭对话框时恢复原速度并暂停。
    - 应用时作为一次可撤销修改：打过的行写入 `timingProvenance = manual`，被后续校对流程视为受保护的时间；上一行若与第一行重叠则收尾；可选“后面没打的行一起平移”（按最后一行的偏差整体平移）。
    - 工程音频未加载时，先通过选中行的试听加载音频，再清除试听窗口并暂停，避免播放到行尾时被截停。
  - **语速异常检查**（`LyricPaceAnalyzer` + 对话框，「校对」菜单和识别摘要的“语速异常 N 行”提示）：
    - 以全曲演唱语速中位数为基准（每秒演唱单位，汉字 1、拉丁字母 0.5）；可比较的行少于 6 行时用默认语速（每单位 0.35 秒），并在界面上注明仅供参考。少于 3 个单位的行不判断。
    - 过快：超过中位数 2.2 倍且每秒至少 6 个单位。若后面有空隙，建议把结束时间延后到中位数时长，但与下一行至少保留 100 ms。
    - 过慢：低于中位数 0.4 倍，并比中位数时长多出至少 2 秒。建议把结束时间提前到中位数时长的 1.4 倍，避免间奏时还显示这一句。
    - 改动不足 300 ms 的建议不列出。手动打轴（`manual` 来源）或手动编辑过的行只提示、不给建议。应用的行记为 `autoRepaired`。只改结束时间，不改文字。
  - **卡拉 OK 导出**（`LyricKaraokeTimingService` + 编码器两种新格式）：
    - 逐字单位：每个汉字、假名或谚文音节为 1；拉丁单词按元音组数估算音节（至少 1）；数字每位 1；空格和标点不占时间，跟随前一个单位显示（行首标点跟随后一个单位）。行时长按权重分配到 10 ms，并把舍入误差累计到后面的单位，保证总和与行时长完全一致。
    - **逐字 LRC**：保留每行的 `[mm:ss.mmm]`，行内写 `<mm:ss.mmm>` 逐字时间，最后以行结束时间收尾。不支持逐字的播放器仍可按行显示。
    - **ASS 卡拉 OK 字幕**：1920×1080，一个 `Karaoke` 样式（唱前白色、唱后蓝色、深色描边），每个单位一个 `\kf` 渐变填色。可选提前 1 秒显示（默认开启），但不早于上一句结束；提前部分是不填色的 `\k`。`{`、`}`、`\` 换成全角，避免被当作覆盖标签。
    - 导出对话框明确说明：逐字时间是按字数估算，不是逐字识别结果。ASS 预览会跳过固定的脚本信息和样式头。
- 影响：
  - 语速阈值（2.2×、6 字/秒、0.4×、2 秒、1.4×）和打轴参数（120 ms 防抖、8 秒间奏、600 ms 外推上限）都是经验值，需要用 #413 的真实歌曲语料校准。
  - 逐字时间在长音、拖腔处会有偏差；需要精确逐字时间时，应在 Aegisub 等工具中细调，或等将来有词级时间戳再接入。
  - 编辑器屏幕没有增加代码。新工具都通过 `LyricBatchTextToolsCoordinator` 接入。
- 状态：生效
- 来源：自选任务（打轴、语速检查、卡拉 OK 交付格式）；[工作日志](log/entries/2026-11-17-1800-add-tap-sync-pace-check-and-karaoke-export.md)

## D-021 保留识别的逐字时间并用于卡拉 OK 导出；识别循环单独检查

- 日期：2026-11-18
- 背景：
  - Qwen3 ForcedAligner 返回的是逐词时间（`timestamps.items` 等），`_groupTokens` 把词组合成行后就丢掉了逐词时间。D-020 的逐字 LRC / ASS 只能按字数估算，长音、拖腔处偏差明显。
  - 语音识别在长音、间奏或伴奏很响时会“卡住”：一行里同一句重复十几遍，或连续多行完全相同。现有的幻觉过滤只看置信度和第二引擎是否覆盖，清理工具只处理“谢谢观看”类水印，都发现不了这类循环。
- 决定：
  - **逐字时间数据**：`LyricLine.words`（`LyricWordTiming` 列表：文字、开始、结束，绝对时间），写入工程 JSON 的 `words` 键；没有时不写，坏条目读入时跳过。Qwen 原生服务保留分组前的逐词时间，也读取段内嵌套的 `words` / `tokens`。分段转写把逐词时间和行一起加上分段偏移。
  - **匹配规则**（`LyricWordTimingService`）：按“演唱字符”匹配——汉字、假名、谚文、字母、数字各算一个，空格和标点不算。只有词的演唱字符数与行文字完全相等时才使用，所以去标点、简繁转换、同音字替换后仍有效，增删字后自动失效（数据保留，改回来又能用）。
  - **跟随行时间**：词都落在行内（容差 60 ms）时原样使用；行被平移、伸缩、打轴或截短后，把词的时间线性映射到行的新区间。因此平移、伸缩、打轴、时间轴修复都不需要改动逐字数据。
  - **使用方**：逐字 LRC 和 ASS 优先用真实逐字时间（每个单位从它第一个演唱字符的开始算起，第一个单位从行首开始），不匹配的行回退到 D-020 的估算；导出对话框显示“N 行使用真实逐字时间”。拆分行时，没有暂停位置就用后半句第一个字的开始作为分界，并把词分到两行；合并两行时，两行都有可用逐字时间才合并逐字时间。检查器显示逐词时间，拖长超过 2.5 秒的词标为警告；文字改动导致失效时给出说明。
  - **识别循环检查**（`LyricAsrLoopDetector` + 对话框，「校对」菜单和识别摘要的“识别循环 N 行”提示）：
    - 行内：1–8 个演唱单位（汉字、假名、谚文音节或拉丁单词）连续重复至少 4 遍；单个汉字类字符至少 8 遍（“啦啦啦啦”是歌词）。6 遍以上（单字 12 遍以上）为明显循环，默认勾选。修复时保留 2 遍（单字 4 遍），前后文字不动。
    - 跨行：连续至少 4 行演唱文字相同（忽略标点、空格和大小写）；6 行以上默认勾选。修复时保留前 2 行，删除其余行，不延长保留行的时间。
    - 手动编辑过的行只提示不修改。被删除的行里的行内循环不再单独列出。应用为一次可撤销修改。
- 影响：
  - 工程 JSON 多了可选的 `words` 字段；旧版本读入会忽略它，再保存会丢掉逐字时间，但不影响行级时间。
  - 行内循环删减后，这一行的逐字时间不再匹配，导出时按字数估算。
  - 循环阈值是经验值，需要用 #413 的真实歌曲语料校准。Whisper 路径目前不提供逐词时间。
  - 编辑器屏幕没有增加代码。新工具通过 `LyricBatchTextToolsCoordinator` 接入。
- 状态：生效
- 来源：自选任务（逐字时间、识别循环）；[工作日志](log/entries/2026-11-18-1200-keep-word-timing-and-add-loop-check.md)

## D-022 逐字打轴写入真实逐字时间；Whisper 逐词时间；循环删减保留逐字时间

- 日期：2026-11-19
- 背景：
  - D-021 让 Qwen 的逐词时间进入了 `LyricLine.words`，但没有对齐器结果的行（Whisper 转写、手工输入的歌词）只能按字数估算，逐字 LRC / ASS 在长音和拖腔处偏差明显。卡拉 OK 歌词的通行做法是人工逐字打轴。
  - whisper.cpp 的 `-ojf` 输出本身就带每个 token 的 `offsets`，解析时被丢掉了。
  - 识别循环检查删减一行里的重复后，整行的逐字时间因为字数不再匹配而失效。
  - 检查器里的逐词时间只能看，不能跳过去听，也不能清掉错误的逐字时间。
- 决定：
  - **逐字打轴**（`LyricWordTapSession` + `LyricWordTapDialog`，「校对」菜单“逐字打轴（卡拉 OK）”）：
    - 单位与卡拉 OK 导出相同（`LyricKaraokeTimingService.units`）：一个汉字、假名、谚文音节或一个拉丁单词，标点跟随前一个单位；没有演唱文字的行（空行、`♪`）跳过。
    - 每唱到一个单位按一下空格（或点大按钮）。60 ms 内的重复按键视为抖动。“按住”模式按下开始、松开结束；Enter 结束当前单位。
    - 单位结束于明确的结束点，否则到下一次按键；超过 `maxCarry` 的停顿不算拖音。一行最后一个单位：下一行首次按键在 1.5 秒内就连到那里，否则取本行平均单位时长（200 ms–1.5 s，单字行取 1.5 s）。单位最短 60 ms。
    - 只有整行按完的行才写入 `words` 和行时间，并记为手动打轴（`LyricTimingProvenance.manual`）；没按完的行保持原样并提示。前一行与第一行重叠时截短前一行。
    - 退格撤回（先撤结束点，再撤按键），R 重打本行，← 后退 3 秒并撤掉之后的打点，可以放慢播放和设置反应补偿。应用为一次可撤销修改。
    - 行级打轴与逐字打轴共用 `LyricTapClock`（播放位置外推、全局偏移、反应补偿）和 `LyricTapPad`。
  - **Whisper 逐词时间**（`WhisperJsonTranscriptParser.segmentWords`）：读取 token 的 `offsets`。带前导空格的 token 开始新词，汉字类字符各自开始新词，纯标点 token 并入前一个词，`[_BEG_]` 等控制 token 跳过。出现 U+FFFD（多字节字符被拆开）、缺少 offsets、越界，或演唱字符数与段文字不一致时，整段不写逐字时间，宁缺毋错。
  - **循环删减保留逐字时间**：`LyricAsrLoopPlan.keptWords` 按演唱字符位置切出保留部分的逐字时间（`LyricWordTimingService.slice`），删减后的行仍可用真实逐字时间导出。
  - **检查器**：逐词时间的每个词可点击，跳到该词开始处播放（加上全局偏移）；“清除”按钮删除这一行的逐字时间，导出改回估算。
- 影响：
  - transcription 的数据层引用 lyrics 领域服务（演唱字符规则），与 lyrics 不引用 transcription 的约束不冲突。
  - 逐字打轴依赖手感，反应补偿默认关闭；放慢播放时补偿按速度缩放。
  - Whisper 只有 `-ojf`（完整 JSON）时 token 才带 offsets；旧的产物没有 offsets，行为与以前相同。
  - 编辑器屏幕没有增加代码，新工具经 `LyricBatchTextToolsCoordinator` 接入。
- 状态：生效
- 来源：D-021 的下一步（逐字打轴、Whisper 逐词时间、循环删减后保留逐字时间）；[工作日志](log/entries/2026-11-19-1200-add-word-tap-sync-and-whisper-word-timing.md)

## D-023 导入卡拉 OK 文件的逐字时间；逐字时间检查；逐字微调

- 日期：2026-11-20
- 背景：
  - 很多人手上已经有卡拉 OK 歌词（逐字 LRC、ASS `\k`、带时间戳的 WebVTT），导入时逐字标签被直接删掉，逐字时间全部丢失。本应用自己导出的逐字 LRC 和 ASS 也无法原样导回。
  - 逐字时间现在有四个来源（Qwen 对齐器、Whisper、导入、逐字打轴），但没有地方能看到哪些行的逐字时间已经失效、被映射，或明显有问题。
  - 逐字时间只能整行重打，不能单独改一个字；没有逐字时间的行也没有办法只调这一行。
- 决定：
  - **导入逐字时间**（`LyricKaraokeTagParser`，由 `LocalLyricFileImportService` 调用）：
    - LRC：增强格式 `<mm:ss.xx>` 和行内方括号 `[mm:ss.xx]` 两种写法；最后一个后面没有文字的时间戳是行尾，在下一行开始之前时作为行结束时间。一行列在多个时间戳下时，逐字时间随每个时间戳平移。
    - ASS：`\k`、`\K`、`\kf`、`\ko` 时长（厘秒）从事件开始累加；开头没有文字的 `\k` 是提前显示的时间，行开始时间改为第一个字开唱的时间。
    - WebVTT：行内 `<hh:mm:ss.mmm>` 时间戳；第一个时间戳之前的文字从字幕开始算起。
    - 每个有演唱文字的片段是一个词，标点并入前一个词，空格去掉；时间倒退的行整行不写逐字时间。
    - 本应用导出的逐字 LRC 和 ASS 可以原样导回（时间精度 10 毫秒）。导入成功提示里显示“N 行带逐字时间”。
  - **逐字时间检查**（`LyricWordTimingAuditor` + 对话框，「校对」菜单，识别摘要的“逐字时间失效 N 行”提示）：
    - 失效：字数与文字不再匹配，导出会忽略。修复为清除。
    - 已映射：行时间改过，逐字时间不在行内，正按比例映射。修复为保存映射结果。
    - 这两项修复都不改变导出结果，默认勾选；文字和行时间不变。
    - 只列出、不修改：拖长 2.5 秒以上的字、不足 40 毫秒的字、行内 1.2 秒以上的停顿（可能应拆行）。
    - 同时显示覆盖情况：多少行有可用逐字时间，多少行导出时按字数估算。
  - **逐字微调**（`LyricWordTimingEditor` + 对话框，从检查器的逐字时间“微调”按钮打开；没有逐字时间的行显示“逐字微调（从估算开始）”）：
    - 选中一个字，调整开始、结束或整体平移（±10 / ±50 毫秒），或设为当前播放位置；可以试听这个字（前 300 毫秒到后 200 毫秒，自动停止）。
    - 首尾相接的两个字共用边界，一起移动；有空隙的两个字保持空隙，直到被推到一起。每个字至少 40 毫秒，最后一个字不越过下一行的开始。
    - 可以与下一个字合并，或把多字词从中间拆开。
    - 行时间默认只在字超出本行时延长；可以选择贴合首尾字。
    - 结果记为手动打轴，应用为一次可撤销修改。没有逐字时间的行从按字数估算的结果开始。
- 影响：
  - 以前导入的 LRC 中若有方括号形式的行内时间戳，过去会留在文字里，现在会被识别为逐字时间。
  - `LyricDraftHealth` 新增 `staleWordRows`。
  - 编辑器屏幕没有增加代码，新工具经 `LyricBatchTextToolsCoordinator` 接入。
- 状态：生效
- 来源：自选任务（逐字时间的导入、检查和微调，D-022 的下一步）；[工作日志](log/entries/2026-11-20-1200-import-check-and-fine-tune-word-timing.md)

## D-024 Qwen3-ASR 按 30 秒分段识别，只发送识别词；识别循环检查覆盖两到四行一组的循环

- 日期：2026-11-21
- 背景：
  - 用户反馈：识别 "Riders on the Storm" 时，大约 1:30 之后同样的两行一直重复，间奏和演唱部分都是这两行，行数暴增。
  - 原因有三层：
    - Elysium Player 总是请求时间戳。runtime 在这条路径上把歌曲切成最长 180 秒的分段（`MAX_FORCE_ALIGN_INPUT_SECONDS`），每段单独解码，再用对齐器对齐。旧文档以为整首歌一段（1200 秒），按 1200 秒算出的每段预算 `max(1024, 256 + 秒数 × 8)` 给四分钟的歌每段 2176 个 token，远多于一段真实歌词。
    - 解码是贪心的，没有重复惩罚。runtime 自带的去重只处理 20 个字符以内、重复 20 次以上的片段，两行一组的循环不受影响。一旦开始循环，就会写满这一段的预算，对齐器再把这些重复的行铺满整段音频，包括间奏。
    - 发送的上下文是 "Song title / Artist / Album"。没有人声的分段里，Qwen 会把它原样写进结果（"Embers. Artist: Avercage."），对齐器把这些词放在前奏、独奏和尾奏上。歌名正好是副歌的歌曲（"Riders on the Storm"）就会出现一遍又一遍的歌名行。
  - 识别循环检查（D-021）只认得行内循环和连续相同的行，A B A B A B 这种两行轮流的循环查不出来。
- 决定：
  - **分段与预算**（`qwen_decode_budget.dart`）：
    - 每次请求都发送 `chunk_max_sec = 30`。
    - 每段预算 `max(256, 128 + min(秒数, 分段秒数) × 8)`：30 秒分段是 368 个 token，180 秒分段最多 1568 个 token。
    - 短分段把循环限制在 30 秒之内，而且解码器经常重新开始，更不容易陷进循环。
  - **上下文**（`qwen_recognition_context.dart`）：
    - 只发送用户为工程填写的识别词（专有名词），逗号分隔，最多 12 个，每个最长 32 个字符。
    - 歌名、歌手、专辑永远不发送。工程识别流程和独立重跑不再拼接 "Song title / Artist / Album"。Whisper 本来就用 `recognitionHints`，不受影响。
  - **只有标点的分段**：
    - 30 秒分段会让对齐器遇到只解码出 "." 的分段（不足一秒的结尾，或间奏）。固定版本的 runtime 遇到这种分段，整个请求会失败，返回 "tokenized word_list is empty"。
    - 新补丁 `tool/patches/qwen3-asr-skip-unalignable-chunks.patch` 像跳过空分段一样跳过没有字母或数字的分段，两个平台的 runtime 构建都应用它。
    - 用旧 runtime 时，Elysium Player 遇到这个错误会按 180 秒分段重试一次，并提示“有一段只识别出标点，正在按较长分段重新识别”。
    - 补丁不计入 `runtimePatchRevision`，已安装的 runtime 不需要修复。bundle manifest 的 `behaviorPatches` 记录它。
  - **元数据**：新增 `qwenChunkSeconds`、`qwenChunkFallback`、`qwenContextTerms`。
  - **识别循环检查**新增“两到四行一组的循环”（`LyricAsrLoopKind.repeatedBlock`）：
    - 2–4 行一组（不全相同、没有空行）首尾相接重复至少 3 遍时列出；4 遍以上默认勾选。修复保留前 2 遍，删除其余的行。手动编辑过的行不删除。
    - 连续相同的行仍然按“连续 N 行相同”处理。几种长度都能匹配时，取覆盖行数最多、组最短的那种。
    - 同一首副歌连唱两遍不会被标记。保留下来的行里如果还有行内循环，照常单独列出。
    - 歌词健康提示的 `loopRows` 计入这些将被删除的行。
- 验证：
  - 用 JamendoLyrics 中带逐行时间标注、CC 授权的英文歌曲，在 GitHub Actions 上用 CPU 版 runtime 实测。歌曲包括 Ridgway、The Rinn、The madpix project、Avercage、Songwriterz、Kinematic，每首四分钟左右，其中三首另做了一版把非演唱部分静音的对照，共 9 次。
  - 最终配置（30 秒分段、不发送标题和歌手、368 token、带新补丁）9 次全部成功：
    - 0.6B 平均词错误率 0.444，60 秒分段为 0.522，30 秒分段带标题为 0.469。
    - 1.7B 为 0.389，60 秒分段为 0.394，30 秒分段带标题为 0.402。
  - 去掉标题和歌手后，演唱行之外的词明显减少：0.6B 从 105 个降到 72 个，1.7B 从 98 个降到 75 个。
  - 没有补丁时，0.6B 在 Ridgway 上因一段 0.54 秒的结尾只解码出 "." 而整首失败；带补丁后成功。
  - 30 秒分段里仍然出现过循环（0.6B 在 Avercage 95 秒处写了 939 个字符；1.7B 在 209 秒处把 "never" 重复了约 180 遍），新预算把它们限制在这一段之内。
  - 旧配置（180 秒分段、每段约 2200 token、带标题）每个模型运行三个多小时后取消。已完成的部分重现了用户反馈的问题：
    - The Rinn 得到 127 行（参考 46 行）、1206 个词（参考 203 个），一组四行从 3:19 起重复了 14 遍；新配置为 31 行、199 个词。
    - 同样四次运行的平均词错误率：0.6B 从 1.05 降到 0.54，1.7B 从 0.54 降到 0.49。
    - 新配置 0.6B 约 35 分钟、1.7B 约 75 分钟跑完全部 9 次。
  - 详细数字见工作日志。
- 影响：

  - 自定义的 `TranscriptionRequest.context` 不再发送给 Qwen。

## D-025 保留对齐器放不下的词；漏唱和声检查

- 日期：2026-11-21
- 背景：
  - D-024 的实测里，歌曲后段的词错误率明显变高（1.7B：开头 0.36，3:00 之后 0.67），主要是结尾反复的和声、口号变短了，有时还提前出现。用户要求在校对时提示“这里可能漏了重复的和声”。
  - 逐词检查 Qwen3 ForcedAligner 的原始结果后发现，大部分“变短”是 Elysium Player 自己造成的：
    - 对齐器放不下的词（多半是识别器写了好几遍的和声）会以**零时长**返回，全部挤在同一时刻，紧接着的一个词被拉长，盖住这段没放好的歌声。例如 Ridgway 结尾：“Whoa I'm paddling on I'm paddling strong Whoa find the fire find the”13 个词都在 223.445 秒，最后的 “fire” 从 223.4 秒拉到 247.9 秒。
    - Qwen 结果解析把 `end <= start` 的词当成无效词丢掉。6 首歌、两个模型的 12 次识别中，每首被丢掉 12%–53% 的词：上面 14 个词只剩一个拉长 24.5 秒的 “fire”，“Find the fire” 连唱 5 遍也只剩下一两遍。
    - D-024 的词错误率是按原始 JSON 的文本算的，用户在编辑器里看到的歌词比那更差。
  - 另外两种痕迹在旧草稿里很常见：一个词被拉长到六秒以上（前奏被第一个词吞掉，行首提前 12–25 秒），以及结尾和声之后留下长空白。
- 决定：
  - **保留零时长的词**（`aligner_word_timing_repair.dart`，Qwen 的逐词解析和分段内逐词时间都使用）：
    - 连续几个词从同一时刻（30 毫秒以内）开始、除最后一个外都没有时长时，视为一组，按字母数分摊这一组的时间范围（从起点到组内最晚的结束）。
    - 范围超过每词 1.2 秒时，把这一组放在范围的**末尾**：实测里被拉长的词从上一个放好的词开始，真正的歌声在它的后段（Ridgway 的和声参考时间是 238–255 秒，拉长范围是 223.4–247.9 秒；前奏被第一个词吞掉时也是如此）。
    - 范围不足每词 80 毫秒时，向下一个词的开始扩展，每词最多 350 毫秒，不越过下一个词。完全没有空间时保留零时长，文字照样进入草稿。
    - 有时长、不在组里的词不变；词的顺序不变。段落级时间戳仍然要求有时长。
  - **漏唱和声检查**（校对菜单，`lyric_missed_repeat_detector.dart`、`lyric_missed_repeat_dialog.dart`），列出三种情况：
    - **逐字时间挤在一起**：一行里至少 5 个词从同一时刻开始（实测 3–4 个很常见且无害）。默认清除这一行的逐字时间，导出时按字数均分；挤在行首时提示开始时间可能偏早。修复前的草稿和其他引擎会出现，修复后的 Qwen 草稿基本不会。
    - **字被拉长**：一个词持续 6 秒以上（实测的拉长词为 6.6–25.6 秒，正常长音很少超过 4 秒）。在行首时把这个词缩到结束前 0.8 秒，这一行的开始时间随之后移，默认勾选；在行尾时可能是长音，缩短这一项不默认勾选；在行中时说明中间漏了歌词，只能试听。逐字时间不在行范围内（行被移动过）时不判断。
    - **这里可能漏了重复的和声**：和声行（大部分是 oh/whoa/la/啦 之类的拟声词、一句短语在行内连唱、或全曲出现 3 次以上的短句）之后至少 8 秒没有歌词，而且这一行在歌曲后 40% 的部分，或者空白之后同一句又出现。歌曲中段和声之后的空白多半是间奏，不报告；反复出现的短句只在结尾报告。最后一行之后的空白需要工程的音频时长。修复是在空白里按原来的间隔插入这一行的副本，最多 8 行，可以用 −/+ 调整行数，默认不勾选；插入的行没有评分，建议再用“打轴”校准。
    - 每一项都可以试听这一行，以及对应的时间段（空白、被拉长的范围、挤在一起的位置）。手动编辑过的行只提示不修改；结果可撤销，保存后才写盘。
    - 歌词健康提示新增“可能漏唱的和声 N 处”（`missedRepeatSpots`，不含需要音频时长的最后一行）。
- 验证：
  - 用 D-024 的 12 次原始识别结果（6 首 CC 授权歌曲 × 2 个模型）按新旧解析分别计算编辑器里看到的歌词的词错误率：0.6B 平均从 0.562 降到 0.437，1.7B 从 0.548 降到 0.383。每首歌都没有变差，Kinematic 从 0.48 降到 0.22。
  - Ridgway（1.7B）结尾从一行 “fire”（223.4–247.9 秒）变成 “Whoa I'm paddling on…” 从 231.1 秒开始的三行，和 “Find the fire” 连唱四遍的一行。
  - 新草稿上，检查列出的主要是前奏被第一个词吞掉的行（Avercage、Kinematic、Songwriterz、The Rinn）和行尾拉长的词。
- 影响：
  - 新识别的草稿行数和词数会变多（找回的词），部分行的开始时间更晚、更接近实际。已有草稿里被丢掉的词找不回来，需要重新识别；漏唱和声检查可以指出它们大概在哪里。
  - 拉长范围里歌声的确切位置仍是推测，找回的词的逐字时间是估算。
- 状态：生效
- 来源：用户反馈与要求（结尾反复的和声被缩短、提前；校对时提示漏了重复的和声）；[工作日志](log/entries/2026-11-21-1800-keep-unplaced-aligner-words-and-check-missed-repeats.md)

## D-026 重新识别一段；参考对齐接受零时长的词

- 日期：2026-11-22
- 背景：
  - 整首识别偶尔只把一段唱错：一句幻觉、一处循环、一段被跳过的和声，其余部分都没问题。此前只能整首重新识别（会覆盖其他行的手动修改），或者手动听写。识别循环检查、漏唱和声检查都只能删掉或复制已有的行，找不回真正唱的词。
  - 改过文字的行会丢掉逐字时间（字数变了，`LyricWordTimingService` 不再使用旧的逐字时间），导出卡拉 OK 时只能按字数均分。
  - D-025 发现 Qwen3 ForcedAligner 会把放不下的词以零时长返回。识别结果的解析已经保留这些词，但参考对齐用的 `ForcedAlignmentHttpClient` 仍然遇到一个零时长的词就让整个请求失败：智能校对 V2 的 ForcedAligner 选项、参考歌词优先的逐行时间提案，在恰好最需要它们的歌（结尾有反复和声）上直接变成“对齐不可用”。
- 决定：
  - **重新识别这一段**（校对菜单，`lyric_span_rerecognition.dart`、`lyric_span_recognition_dialog.dart`、`project_span_recognition_service.dart`）：
    - 选择从第几行到第几行（默认是当前选中的行），以及向前、向后延伸多少：不延伸、0.5 秒（默认）、1 秒、2 秒，或“到上一行/到下一行”。延伸不会越过相邻的行（否则会把相邻行再识别一遍）；行之间本来就重叠时，只用选中行自己的范围。选“到下一行”可以识别两行之间的空白，找回漏掉的歌词。
    - 范围在 0.5–90 秒之间。更长的范围更适合整首重新识别；Qwen3-ASR 本来就按 30 秒分段解码。
    - 三种方式：Qwen3-ASR 重新识别、Whisper 重新识别（新文字和时间，替换选中的行），以及按现有文字重新对齐（保留文字，只重新计算行和逐字的时间）。
    - 数据层用 FFmpeg 把这一段剪成独立的 16 kHz 单声道片段，识别器只看到这一段；结果再平移回整首歌的时间轴，并按文档的整体偏移换算。不读写歌词文档和工程；运行期间持有共享的 ASR 资源租约（新增 `AsrResourceUse.spanRecognition`），与整首识别、对齐、runtime 安装互斥。Qwen3-ASR 使用应用共享的 Qwen 服务：整首识别后十分钟内模型仍在内存里，可以直接复用，也不会在同一块显卡上再启动一个模型服务；Whisper 每次用新的实例，用完释放。重新对齐复用参考对齐的就绪检查，但不再单独申请租约。
    - 识别结果裁剪到处理范围内，按时间排序、去掉重叠，裁剪后不足 120 毫秒的片段舍弃；逐字时间被裁掉一部分时整行丢弃逐字时间（导出时按字数均分）。选中的行全是合唱行时，新行也标为合唱。
    - 预览显示当前的行和新识别的行、文字相似度（忽略大小写、空格和标点的编辑距离），以及范围内手动编辑过的行数（替换会覆盖它们，事先提示）。行数相同时可以只替换文字、保留原来的时间和行 id；文字有变化的行丢掉逐字时间。
    - 重新对齐时只把有歌词文字的行发给对齐器；对齐结果按顺序逐字匹配（忽略大小写、空格和标点），一个合并过的词跨过行尾时两行都用它的时间。任何对不上、没对齐完、多出来的词都让整个结果作废，不给出部分时间。
    - 确认后作为一次可撤销的修改应用，保存后才写盘。运行中可以停止；关闭对话框也会停止。没有音频或没有本地识别运行时时，菜单项给出原因而不是打开空对话框。
  - **参考对齐接受零时长的词**（`ForcedAlignmentHttpClient`、`AlignerWordTimingRepair.repairToTimedSpans`）：
    - 返回的词允许结束时间等于开始时间（结束早于开始、超出音频长度、开始时间倒退仍然拒绝）。
    - 先用 D-025 的修复分摊挤在一起的词，再按音频长度截断；仍然没有时长的词并入前一个有时长的词（文字用空格连接、时间不变），开头的并入后一个。去掉空白后文字和顺序不变，所以参考对齐的严格逐字匹配仍然成立；只有所有词都没有时长时才报错。
    - 这样智能校对 V2 的两种 ForcedAligner 用法和新的“按现有文字重新对齐”都不会再因为一段和声整体失败。
- 影响：
  - 模型没有加载时（例如整首识别已经过去十分钟以上），第一次运行要先加载模型，可能要几十秒。
  - 片段边缘的词可能被截断或重复识别；默认 0.5 秒延伸是折中，必要时可以调整。
  - 合并进相邻词的零时长词没有自己的时间，逐字时间按合并后的词计算。
- 状态：生效
- 来源：自选任务（识别、校对实用功能）；[工作日志](log/entries/2026-11-22-1200-rerun-a-stretch-and-accept-zero-length-alignment.md)

## D-027 Whisper 关闭跨窗口文字历史；跨行循环重新识别并交给 Qwen 仲裁

- 日期：2026-11-23
- 背景：
  - #467（D-024）之后，用户反馈歌曲后半段仍然会把一两句歌词无限重复。D-024 只处理了 Qwen 的循环；这次的循环来自 Whisper。
  - whisper.cpp 按 30 秒窗口解码，默认把之前解码出的文字（最多 224 个 token）作为下一窗口的上下文。窗口一旦重复了上一对句子，下一窗口的上下文里就有两遍，更容易继续重复，直到歌曲结束。v1 歌词档位还把歌名、歌手作为初始提示放进同一个上下文。
  - 每个循环行本身看起来是正常的一行，D-021/D-024 的行内和行间循环检查只在校对时提示；识别融合只比较单行，Whisper 为主时循环行原样保留，Qwen 为主时循环行逐行补成“建议补入”。
  - 用 6 首 JamendoLyrics CC 授权歌曲、large-v3、固定的 whisper.cpp `927cfce` 在 GitHub Actions 上对比三种参数（词错误率 / 后半段词错误率）：
    - v1（歌名歌手提示 + 文字历史）：平均 0.815；6 首中 4 首循环或幻觉，最长的是 Ridgway 217 秒起两行一组重复 29 遍，Avercage 全曲只有“作詞・作曲・編曲 初音ミク”。
    - 标准参数（只有文字历史）：平均 0.687；Avercage 从 2 秒起两行一组重复 60 遍，The Rinn 从开头重复 27 遍。
    - `--suppress-nst --max-context 0`（不带提示）：平均 0.354，6 首都没有成组循环，通常也最快。Kinematic 后半段从 1.608 降到 0.365。
  - Qwen 每个 30 秒分段独立解码，不带前文，同一首歌的后半段识别正确。
- 决定：
  - **歌词档位改为 `whisper-lyrics-v2`**：`--suppress-nst --max-context 0`，不再发送 `--prompt`。whisper.cpp 只通过同一个文字历史读取初始提示，`--max-context 0` 时提示本来就不生效；实测提示让结果更差。运行时不支持 `--max-context` 时只保留 `--suppress-nst`，都不支持时回退到标准参数并记录。提示词生成仍保留在断点续跑指纹里。
  - **跨行循环检测**（`AsrSegmentLoopDetector`，transcription 领域层）：同一行连续至少 3 遍，或 2–4 行一组连续至少 3 遍；6 行 / 4 组以上，或循环行一半以上每秒超过 7 个词（汉字、假名按字计）时为强循环。比较时忽略大小写、标点和相邻重复的词。时间戳被压成约 1 秒一行时，循环前同样被压缩的几行（最多 12 行）算作引入段。
  - **只重新识别循环的一段**（`WhisperLoopRecoveryPolicy` `whisper-loop-redecode-v1`）：首遍保留了文字历史（标准档位，或运行时拒绝了参数）且有强循环时，用 `--offset-t/--duration --max-context 0` 只重新识别这一段（至少 8 秒、最长 4 分钟、每首最多 3 段，语言沿用首遍检测结果），新结果本身不循环才替换。首遍已经关闭历史时不再重复同样的识别，直接交给融合。重新识别失败不会让整次识别失败。
  - **融合仲裁**（`WhisperLoopArbiter`，四条融合路径都使用）：比较 Whisper 循环和 Qwen 在同一段音频里听到的内容：
    - Qwen 听到的是不同的、不循环的歌词：用 Qwen 的行替换循环（连同被压缩的引入段），每行都进入复核队列，置信度不超过 60。
    - Qwen 也听到差不多次数的重复（至少 2 遍且不少于一半）：歌词本来就重复，保留。

## D-028 错误不再静默吞掉；下载地址和断点续传各只有一份实现

- 日期：2026-11-24
- 背景：
  - #460：`lib` 里有 39 处 `catch (_) {}`。其中 11 处是 9 个文件存储各自手写的同一个写入链（先等上一次写入、忽略它的错误、再写），其余分布在录音回滚、麦克风停止、封面缓存、Media Hub 上传清理、ASR 进程终止和打点窗口的播放控制里。打点窗口里播放器拒绝播放时按钮没有任何反应，也没有日志。
  - #461：Hugging Face、ModelScope、GitHub release 和 FFmpeg 下载地址散落在 5 个文件里，仓库 owner 写死了两次；切镜像或 fork 时容易漏改。
  - #462：三个运行时安装器各有一份断点续传下载循环，而且已经不一致：`ResilientAsrRuntimeManager` 收到 206 时不检查 `Content-Range` 起点，也不检查最终大小。
- 决定：
  - **写入链**：新增 `core/persistence/SerialWriteQueue`。写入严格串行；某次写入失败只让发起它的调用者失败，后面的写入照常进行；`idle` 等待已排队的写入且不抛错。9 个文件存储改用它。
  - **尽力而为的步骤**：新增 `core/diagnostics/bestEffort`（以及 `bestEffortSync`、`bestEffortValue`）。调用处必须写明这一步是什么、失败影响多大：`housekeeping`（删临时文件、取消订阅等）记 debug，不带堆栈；`degraded`（可能占用麦克风、缓存不再清理、留下半个上传文件）记 warning 并带堆栈，会进入诊断报告。只用于继续执行确实正确的地方；调用者需要处理的错误仍然向上抛。
  - 日志系统自己的 sink 失败无法再写日志，`app_logger` 的 flush、`crash_capture`、`file_log_sink` 保留忽略，并写明原因。
  - **打点窗口**：播放、暂停、跳转、调速失败时在窗口里显示“…失败：播放器没有响应”，并记 warning；下一次成功的操作清除提示。关闭窗口时的暂停和恢复速度只记日志。
  - **ASR 地址**：新增 `AsrEndpoints`，transcription 目录里只有它可以写 `https://` 或 `Uri.https(`。发布仓库默认 `BrainEno/lyric-forge-ktv`，fork 可用 `--dart-define=LYRICFORGE_RELEASE_REPOSITORY=owner/name` 覆盖。固定版本、文件名和 SHA-256 仍放在校验它们的代码旁边。
  - **断点续传**：新增 `ResumableFileDownload` 和 `AsrTransferCancellation`，三个安装器都通过它下载：
    - 已有的 `.part` 只在服务器返回 206 且 `Content-Range` 正好从它的长度开始时续传，返回 200 时从头下载，其他 206 删除 `.part` 并报错；
    - 结果必须等于已知大小：短了保留 `.part` 供下次续传，长了删除；
    - 每个数据块都检查取消；取消会中止正在进行的请求，并关闭对应的 client。
    - 各安装器只负责把失败类型翻译成自己的提示，并在校验摘要后才替换目标文件。
  - **防回退**：`test/architecture/source_hygiene_test.dart` 禁止空的 `catch` 块、logger 以外的空 `catchError`、feature 里的手写 `_writeChain`、theme 以外的颜色字面量（#458），以及 `AsrEndpoints` 以外的 transcription 远程地址。
- 影响：
  - 原来静默的失败现在会出现在日志里；debug 级别只在开启详细诊断时记录。
  - 运行时引擎和 FFmpeg 下载失败的提示改用实际组件名，不再一律写成 “Whisper large-v3”。
  - `ResilientAsrRuntimeManager` 的 Whisper runtime 下载现在也会拒绝不一致的续传响应，并检查大小。
- 状态：生效
- 来源：issue #458、#460、#461、#462、#464；[工作日志](log/entries/2026-11-24-1200-issue-cleanup-errors-endpoints-downloads.md)
